# ADR-022 관리자 토큰의 구현: Spring Security 관리 체인 하나, 토큰 형식, 셸에서 WebView 로의 전달

- 상태: 제안
- 날짜: 2026-11-22
- 구현: 구현됨 (P1-03, 2698115) — Windows·Linux 의 셸은 미검증(PLAT-1)

## 맥락

[ADR-021](ADR-021-admin-token-bearer.md)은 무엇을 지킬지 정했다. 이 ADR 은 P1-03 의 계획과 구현에서 정한 방법을 적는다. 설계는 이 세부를 정하지 않았다.

## 결정

1. **Spring Security 와 관리 체인 하나.** `spring-boot-starter-security`(Boot BOM 이 관리, 버전 덮어쓰기 없음)를 쓴다. `com.queryhub.adapter.web.admin.security` 에 `SecurityFilterChain` 을 하나만 둔다. 매처는 경로를 두 가지로 본다: 디코딩하고 정규화한 서블릿 경로(`servletPath` + `pathInfo`, Spring MVC 가 핸들러를 찾는 경로)와 디코딩하지 않은 요청 URI(context path 를 뺀 값)다. 어느 한 쪽이라도 소문자로 바꿔 `/admin` 이거나 `/admin/` 으로 시작하거나, health 세 경로 밖의 `/actuator/**` 이면 체인이 맡는다. `/actuator` 접두사와 서블릿 경로 `/` 는 고정 전제다. 그래서 `management.endpoints.web.base-path` 가 `/actuator` 가 아니거나, `management.server.port` 로 actuator 를 다른 포트에 열거나, `spring.mvc.servlet.path` 가 `/` 가 아니면 두 프로파일 모두 기동을 거부한다(P1-03 2회차 확인: 1회차 JAR 은 `spring.mvc.servlet.path=/qh` 에서 `/qh/admin/api/v1/runtime` 을 토큰 없이 200 으로 답했다). 2회차 리뷰가 같은 종류의 우회 둘을 더 재현했다: `spring.security.filter.dispatcher-types` 에서 REQUEST 를 빼면 체인이 일반 요청에 돌지 않아 토큰 없이 200 이었고, `management.endpoints.web.path-mapping.*` 로 env 를 열린 `/actuator/health` 로 옮기면 토큰 없이 env 가 나왔다. 그래서 3회차부터 두 프로파일 모두 다음 설정에서도 기동을 거부한다: dispatcher-types 가 Boot 기본 다섯 가지(request, error, async, forward, include)를 다 갖지 않을 때, `management.endpoints.web.path-mapping.*` 에 값이 있을 때, `management.endpoint.health.probes.add-additional-paths=true` 이거나 `management.endpoint.health.group.*.additional-path` 에 값이 있을 때(토큰 없이 여는 경로를 health 세 경로로 둔다), `server.tomcat.accesslog.pattern` 에 `Authorization` 이 들어갈 때(대소문자 무관, 토큰이 접근 로그에 남는다), `spring.mvc.log-request-details=true` 일 때(DispatcherServlet 의 TRACE 로그가 헤더 값을 적는다). 값은 Boot 가 쓰는 속성 클래스(`SecurityFilterProperties`, `WebEndpointProperties`, `HealthEndpointProperties`)로 바인딩해 읽으므로 이름 변형과 환경변수 형태를 Boot 와 같게 푼다. 속성 목록은 알려진 길만 막는다. 그래서 그 뒤에 필터 매핑 검사와 기동 직후의 자기 점검을 둔다(결정 6). 체인은 상태가 없다: 세션, CSRF(쿠키가 없으므로), 요청 캐시, 폼 로그인, HTTP Basic, 로그아웃, 익명 사용자를 끄고 Spring Security 의 기본 보안 헤더는 둔다. `UserDetailsServiceAutoConfiguration` 은 제외해 메모리 사용자와 생성된 비밀번호 로그가 없다. 다른 체인이 없으므로 health, `/error`, `/api/v1/**` 는 `FilterChainProxy` 의 방화벽(StrictHttpFirewall)만 거친다.
2. **필터 순서:** 네트워크 검사(루프백, Host) → CORS → 토큰 → `authenticated()`. 네트워크 검사가 CORS 보다 앞이므로 사전 요청에도 적용된다.
3. **토큰 검사:** `Authorization` 헤더가 정확히 하나이고 `Bearer <토큰>`(scheme 대소문자 무관, 공백 하나)일 때만 받는다. 그 밖(헤더 없음, 빈 토큰, Basic, 헤더 둘, 쿼리 파라미터의 토큰)은 401 이다. 받은 값과 설정 값의 SHA-256 다이제스트를 `MessageDigest.isEqual` 로 비교한다. ArchUnit R9 가 검증기 클래스의 `String.equals` 류와 `Arrays.equals` 사용을 막는다.
4. **응답:** 401 은 공통 오류 형식 `UNAUTHORIZED`(고정 메시지), `WWW-Authenticate: Bearer`, `X-Request-Id` 다. 없는 토큰과 틀린 토큰의 응답은 requestId 말고 같다. 네트워크 검사 실패는 403 `FORBIDDEN` 이다. 응답 JSON 은 애플리케이션의 Jackson 매퍼로 쓴다(`sendError` 를 쓰지 않는다).
5. **토큰 출처와 형식:** `QUERYHUB_ADMIN_TOKEN`(`queryhub.admin.token` 에 느슨하게 바인딩) 또는 `QUERYHUB_ADMIN_TOKEN_FILE`(4 KiB 이하, 끝의 LF 나 CRLF 하나를 지운다). 32-512 자, RFC 6750 b64token 문자(`[A-Za-z0-9-._~+/]+=*`). 둘 다 없거나 둘 다 있거나, 파일이 없거나 읽을 수 없거나 비었거나 크거나, 형식이 틀리거나, 명령행 인자·JVM 시스템 속성·그 두 곳의 `spring.application.json` 에서 오면 포트를 열기 전에 기동을 거부한다. 메시지는 변수나 속성 이름만 말한다. 토큰은 설정 속성 클래스에 바인딩하지 않는다(`toString` 과 바인딩 오류 메시지에 나오지 않게). [ADR-011](ADR-011-metadata-secrets-env-only.md)의 프로세스 출처 검사는 공용 `ProcessVisibleSources` 로 옮겼고 Metadata DB 의 동작과 메시지는 그대로다.
6. **루프백 판정:** `request.getRemoteAddr()` 를 DNS 없이 IP 리터럴로 읽어 `127.0.0.0/8`, `::1`, `::ffff:127.0.0.0/104` 만 루프백으로 본다. 읽지 못하면 거부한다. 이 값이 소켓의 원격 주소라는 전제는 allow-remote 가 false 일 때 아래 두 겹의 기동 검사로 지킨다. 둘 중 하나라도 실패하면 포트를 열기 전에 기동을 거부하고, 메시지는 속성 이름이나 valve 클래스만 말한다.
   - **속성:** `server.forward-headers-strategy` 가 none 이 아니거나(`application.yml` 은 none 이다), `server.tomcat.remoteip.*` 속성 중 하나라도 값이 있으면 거부한다. 속성 이름 하나가 아니라 접두사 전체로 판단한다. Boot 4.1.2 는 forward 헤더가 켜졌을 때뿐 아니라 `remote-ip-header` 나 `protocol-header` 에 값이 있을 때도 RemoteIpValve 를 넣고, 그 valve 의 기본값은 `X-Forwarded-For` 와 사설 대역의 내부 프록시다(1회차 리뷰 R1 이 재현했다).
   - **파이프라인:** 만들어진 내장 Tomcat 의 engine, host, context, wrapper 파이프라인을 허용 목록(Tomcat 기본 valve, `ErrorReportValve`, `NonLoginAuthenticator`, 접근 로그 valve)으로 검사한다(`TomcatRemoteAddressGuard`). RemoteIpValve 와 하는 일을 알 수 없는 valve 는 모두 거부한다. 검사는 phase 가 가장 낮은 `SmartLifecycle` 이다. 웹 서버는 refresh 의 onRefresh 에서 만들어지고 포트는 그 뒤 WebServerStartStopLifecycle 이 열므로, 검사가 실패하면 커넥터가 시작되지 않은 채 컨텍스트가 닫힌다. Tomcat 이 아닌 웹 서버도 거부한다.
   - **필터 매핑 (두 프로파일, 3회차):** 같은 시점(포트를 열기 전)에 `TomcatSecurityFilterGuard` 가 context 의 필터 매핑을 본다. `springSecurityFilterChain` 이 URL 패턴 `/*` 와 dispatcher 다섯 가지로 매핑되어 있어야 하고, 그 앞의 URL 패턴 필터는 허용 목록(Boot 의 문자 인코딩·폼·요청 문맥·hidden method 필터, `ServerHttpObservationFilter`, `RequestIdFilter`)만 될 수 있다. `ForwardedHeaderFilter` 는 allow-remote 가 true 일 때만 앞에 올 수 있다. 등록이 꺼지거나 다시 등록되거나 dispatcher 가 줄거나 확인되지 않은 필터가 앞에 있으면 기동을 거부한다. 메시지는 필터 이름과 클래스만 말한다. 4회차(리뷰 C3-R6): 그 이름의 필터가 `DelegatingFilterProxy`(Boot 의 등록 빈이 만드는 것)인지도 본다.
   - 그래서 allow-remote 가 false 이면 `X-Forwarded-For`, `X-Forwarded-Proto`, `Forwarded` 는 루프백 판정에 쓰이지 않는다. 보안 필터 앞에 원격 주소를 바꾸는 필터(예: `RemoteIpFilter` 를 직접 등록)를 두면 필터 매핑 검사가 거부한다. 보안 필터 뒤의 필터는 루프백 판정보다 늦게 돈다.
   - **자기 점검 (두 프로파일, 3회차):** 속성과 매핑 검사가 모르는 길로 체인이 꺼지거나 핸들러가 옮겨져도 그대로 서비스하지 않도록, `AdminChainSelfProbe` 가 포트를 연 직후(WebServerStartStopLifecycle 바로 뒤의 phase, 아직 refresh 안) 자기 포트로 평문 HTTP/1.1 을 보낸다: 주소는 `server.address`(비었거나 와일드카드면 루프백), `Host: localhost`, 토큰 없음, 연결·읽기 제한 5 초, 소켓만 쓴다. `/admin/api/v1/runtime`, `/actuator/env`, `/actuator/beans` 는 체인의 401(`WWW-Authenticate: Bearer`, `UNAUTHORIZED`)이나 403 `FORBIDDEN`(Host 검사가 `localhost` 를 받지 않는 server 설정 등)이어야 하고, health 세 경로는 health 문서(상태 코드와 상관없이 최상위 키가 `status`, `components`, `groups`, `description` 뿐인 JSON)나 404 `NOT_FOUND` 여야 한다. 2xx, 404, 그 밖의 응답, 응답 없음이면 refresh 가 실패해 포트가 닫히고 프로세스는 0 이 아닌 코드로 끝난다. 메시지는 경로와 상태 코드만 말한다. readiness 의 ACCEPTING_TRAFFIC 은 refresh 뒤에 나오므로 점검이 통과하기 전에는 readiness 가 200 이 아니다. 점검하는 동안(로컬 시험에서 대개 수 ms ~ 수십 ms) 포트는 열려 있다. 응답 본문은 JSON 으로 읽는다(오류 응답의 `error.code`, health 문서의 최상위 키). 그래서 `spring.jackson.serialization.indent-output` 같은 출력 형식 설정과 상관없다(4회차, 리뷰 C3-R2). 소켓은 프록시를 거치지 않는다(`Proxy.NO_PROXY`, C3-R5). 실패하면(4회차, 리뷰 C3-R1) 경로와 상태만 담은 이유를 먼저 ERROR 로그에 남기고, `StartupFailureHalt` 예약(15 초 뒤에도 JVM 이 살아 있으면 `Runtime.halt(1)`, `QueryHubApplication.main` 으로 시작한 프로세스만)을 건 뒤 예외를 던진다. 메타데이터 DB 가 멈추면 health 점검이 끝나지 않고 컨텍스트 정리(Hikari 종료)도 멈출 수 있기 때문이다. health 경로가 5 초 안에 답하지 않으면 엔드포인트가 옮겨졌다고 하지 않고 시간 초과를 따로 말한다. DB health 점검 자체에 시간 제한을 두는 방법도 있지만(JDBC socketTimeout 등) 메타데이터 DB 의 모든 질의에 영향을 주고 다른 health 기여자가 멈추는 경우는 막지 못하므로, 점검 쪽의 시간 초과 처리와 강제 종료 예약으로 정했다. 그래서 기동 직후 DB 가 멈추면 런타임은 health DOWN 으로 떠 있지 않고 이유를 남기고 끝난다(실패 닫힘). 내장 TLS(`server.ssl.*`, SSL 번들 포함)는 4회차부터 속성 검사가 포트를 열기 전에 거부하고(Boot 의 `Ssl.isEnabled` 와 같은 조건), 그래도 TLS 커넥터가 생기면 이 점검이 이중 안전장치로 거부한다. TLS 는 앞단 프록시에서 끝낸다(아래 「근거」의 사람 결정). 한계: 점검은 여섯 경로만 본다. 그 밖의 관리 경로만 체인 밖으로 옮기는 설정은 이 점검으로 잡지 못하고 속성·매핑 검사에 기댄다. 2회차까지의 우회 셋(서블릿 경로, dispatcher 종류, path-mapping)은 모두 이 여섯 경로를 함께 움직인다.
7. **Host 규칙:** 원본 `Host` 헤더가 정확히 하나이고 `이름[:포트]` 여야 한다. 이름은 대소문자 없이 `localhost`, `127.0.0.1`, `[::1]` 이나 `queryhub.admin.allowed-hosts` 의 항목이고, 포트는 있으면 1-65535 의 숫자다(로컬 포트와 비교하지 않는다. 개발 서버의 `localhost:1420` 이 통과한다). `request.getServerName()` 도 허용된 이름이어야 한다(절대 형식 요청 대상). 허용되지 않은 이름, 끝의 점, 다른 127.x 표기, 범위 밖 포트(`localhost:0`, `localhost:65536`), HTTP/1.0 의 Host 없음은 가드의 403 `FORBIDDEN` 이다. 형식이 깨진 Host 와 요청 대상 일부는 애플리케이션이 실행되기 전에 Tomcat 의 평문 400 이 된다(공통 오류 형식이 아니고 `X-Request-Id` 가 없다). 1회차 시험에서 확인한 형태: 대괄호 없는 IPv6(`::1`), zone id(`[::1%25lo0]`), userinfo(`user@localhost`), 숫자가 아닌 포트(`localhost:abc`), Host 헤더 둘, HTTP/1.1 의 Host 없음, 절대 형식 요청 대상. 어느 쪽이든 관리 API 에 닿지 않는다([BACKLOG](../BACKLOG.md) P103-4). `allowed-hosts` 항목(호스트 이름, IPv4, 대괄호 IPv6, 와일드카드와 포트 없음)이 틀리면 기동을 거부한다.
8. **CORS 는 체인 안:** `WebMvcConfigurer` 매핑 대신 관리 체인의 `cors()` 가 쓰는 `CorsConfigurationSource` 다. 허용 요청 헤더는 `Authorization` 하나, 메서드는 GET, 자격 증명 없음, 사전 요청은 토큰 없이 답한다. 요청한 헤더가 모두 허용될 때만 사전 요청을 통과시킨다(Spring 의 기본은 일부만 맞아도 통과시킨다). 허용 출처의 401 에도 `Access-Control-Allow-Origin` 이 한 번 붙는다. [ADR-015](ADR-015-desktop-fixed-port-and-cors.md)를 바꾼다.
9. **경로 방화벽:** 관리 체인 경로(`/admin/**`, `/actuator/**`)의 퍼센트 인코딩은 모두 400 이다(`AdminPathFirewall`, `/admin/api/v1/%72untime` 같은 우회를 막는다). `/actuator` 탐색은 끄고(`management.endpoints.web.discovery.enabled: false`), 토큰을 확인한 뒤의 `/actuator/health/<그 밖>` 은 404 `NOT_FOUND` 다. 서블릿 컨테이너(Tomcat)가 애플리케이션보다 먼저 거부하는 깨진 요청 대상(`/admin%2Fapi/v1/runtime`, `/admin/api/v1/runtime%00`, `{` 나 `}` 가 들어간 대상)과 §7 의 깨진 Host 는 Tomcat 의 400 이고 공통 오류 형식이 아니다. 사용자 정의 Tomcat 오류 밸브는 만들지 않는다.
10. **셸의 토큰:** `getrandom` 0.3.4(Cargo.lock 에 이미 있던 버전을 직접 의존으로 더했다)로 32 바이트를 받아 소문자 16진수 64 자로 만든다. Tauri `setup` 에서 셸 프로세스마다 한 번 만들고, 실패하면 setup 이 실패한다(토큰 없이 런타임을 띄우지 않는다). `AdminToken` 의 Debug 와 Display 는 값을 보이지 않는다. 셸 자신의 환경에 있는 `QUERYHUB_ADMIN_TOKEN`, `QUERYHUB_ADMIN_TOKEN_FILE` 은 넘기지 않는다. 자식 출력의 가림은 Metadata DB 비밀번호와 토큰을 함께 가린다. 상태(`RuntimeStatus`, `Failure`)에는 토큰이 없다.
11. **WebView 로의 전달:** 인자 없는 Tauri 커맨드 `admin_token` 이 토큰을 돌려준다. `build.rs` 의 앱 매니페스트에 등록하고, `capabilities/default.json` 이 `allow-admin-token` 을 main 창에만 준다(`remote` 키 없음, 앱에 묶인 로컬 출처만). UI 는 토큰을 한 번 받아 메모리에만 두고(localStorage, sessionStorage, 화면, 로그에 남기지 않는다) `Authorization: Bearer` 헤더로만 보낸다. 토큰이 없으면 요청하지 않는다. 401 과 403 은 서로 다른 고정 한국어 문장이다.

## 검토한 대안

- **명령행 인자로 토큰 전달(`--queryhub.admin.token=`):** 프로세스 목록에 보인다. ADR-011 과 같은 이유로 버렸고, 런타임은 이 경로를 거부한다.
- **앱 데이터 디렉터리의 토큰 파일:** 파일 권한, 정리, 경쟁 조건을 따로 다뤄야 한다. 환경변수는 설계 §1.2 가 이미 받아들인 경로다. server 의 시크릿 파일(`QUERYHUB_ADMIN_TOKEN_FILE`)은 컨테이너 배포를 위해 둔다.
- **WebView 에 토큰 주입(URL 쿼리, 초기화 스크립트, 전역 변수):** URL 은 기록과 로그에 남고, 초기화 스크립트는 창이 탐색한 다른 페이지에도 실행될 수 있다. 커맨드와 capability 는 main 창의 로컬 출처로 범위를 좁힌다.
- **쿠키 세션:** CSRF 방어가 필요하고 설계 §7 이 Bearer 를 정했다.
- **Spring Security 없이 서블릿 필터 하나:** 경로 정규화 공격을 막는 방화벽과 검증된 필터 체인을 직접 만들어야 한다.
- **`String.equals` 비교:** 시간 차로 토큰을 추측할 수 있다. R9 가 막는다.
- **`X-Forwarded-For` 를 믿는 루프백 판정, 거부 목록 방식의 Host 검사:** 둘 다 요청을 보낸 쪽이 바꿀 수 있다.
- **Tomcat 오류 밸브로 컨테이너 400 도 공통 형식으로:** 애플리케이션 코드가 실행되지 않는 거부이고 응답에 데이터가 없다. 만드는 값에 비해 얻는 것이 적어 P1-03 진행 중(2026-11-22) 받아들이지 않기로 했다([BACKLOG](../BACKLOG.md) P103-4).

## 결과

- 행동 변화: 방화벽의 400(모든 경로의 `;`, `//`, `/./` 등), 관리 체인 경로의 퍼센트 인코딩 400, `/actuator` 탐색과 health 하위 경로 제공 중단, 거부된 CORS 요청은 여전히 Spring 의 403 본문. [API_SPECIFICATION.md](../API_SPECIFICATION.md)와 [SECURITY.md](../SECURITY.md)에 있다.
- 기동 거부 조건이 늘었다(2회차): allow-remote 가 false 일 때의 `server.tomcat.remoteip.*` 와 파이프라인 valve, 두 프로파일의 actuator 기본 경로·관리 포트·서블릿 경로. 3회차: 두 프로파일의 `spring.security.filter.dispatcher-types`, `management.endpoints.web.path-mapping.*`, health 추가 경로, 접근 로그 패턴의 `Authorization`, `spring.mvc.log-request-details=true`, 필터 매핑, 내장 TLS, 자기 점검 실패(포트를 연 뒤 멈춘다). 4회차: 내장 TLS 거부를 포트를 열기 전(속성 검사)으로 옮겼고, 보안 필터가 DelegatingFilterProxy 인지 보며, 자기 점검 실패는 이유를 먼저 로그에 남기고 정해진 시간 안에 끝난다. [DEPLOYMENT.md](../DEPLOYMENT.md)의 「기동 거부 설정」에 있다.
- 시험: runtime 단위·웹 시험(실제 포트와 원시 소켓), 통합 시험(토큰 없는 JAR 은 0 이 아닌 코드로 끝나고 포트를 열지 않는다), cargo test, vitest. 수는 [TEST_PLAN.md](../TEST_PLAN.md)에 있다.

## 근거

- 내장 TLS 거부: 3회차 리뷰(C3-R4)가 확인을 요청했고, 사용자가 2026-11-22 「받아들임 (권장)」을 골랐다. 고른 선택지의 문구: "TLS는 앞단 프록시에서 처리하는 것을 전제로 합니다. 거부 시점을 포트가 열리기 전으로 당기고, 배포 문서에 명시합니다. 런타임 자체 HTTPS 지원은 BACKLOG에 남겨 Phase 8(배포)에서 다시 봅니다." 런타임 자체 HTTPS 는 [BACKLOG](../BACKLOG.md) P103-7 이다.
- P1-03 의 요구사항과 계획(팩토리 태스크 T-20261122-093948-3537)에서 정했다. 사용자가 명시적으로 결정하지 않았으므로 제안이다. 사용자가 받아들이면 승인됨으로 바꾼다.
